# 运维手册

面向 CLIProxyAPI 用户与运维人员。安装、配置、备份、保留策略、故障处理都集中在这里；
更深的设计约束见 [`IMPLEMENTATION.md`](IMPLEMENTATION.md)，接口速查见
[`../README.md`](../README.md)。

## 1. 安装与启动

### 目录与 id

宿主按 `<plugins.dir>/<goos>/<goarch>/<文件名>` 发现原生库，并用**文件名去掉扩展名**
作为插件实例 id。发布归档里的库名是 `cliproxyapi-credit-manager.so`（macOS 为
`.dylib`），所以：

- 实例 id：`cliproxyapi-credit-manager`
- 配置块：`plugins.configs.cliproxyapi-credit-manager`
- 界面地址：`/v0/resource/plugins/cliproxyapi-credit-manager/index.html`
- 客户自助地址：`/v0/resource/plugins/cliproxyapi-credit-manager/lookup.html`
- **管理 API 前缀是插件自己声明的固定值**：`/v0/management/plugins/credit-manager/api/…`
  （与实例 id 不是同一个字符串，不要混用）

**保留发布文件名，不要重命名。** 插件只接受实例 id `cliproxyapi-credit-manager`。
其它资源基路径会停止新请求准入，避免执行后丢弃无法归属的用量。

安装步骤（主机上执行）：

#### 方式 A：通过 CPA 插件商店（推荐）

在 CPA 的 `config.yaml` 的 `plugins` 下添加自定义源：

```yaml
plugins:
  enabled: true
  dir: "./plugins"
  store-sources:
    - "https://raw.githubusercontent.com/fengwk/cliproxyapi-credit-manager/main/registry.json"
```

随后在 CPA Web 控制面板的「插件商店」中即可直接发现并安装本插件。

#### 方式 B：手动下载安装

```sh
# 1. 校验下载物
sha256sum -c checksums.txt --ignore-missing   # 需要与 zip 同目录

# 2. 解压，只复制动态库
# VERSION 设为所下载的版本号，不含 v 前缀
unzip -o "cliproxyapi-credit-manager_${VERSION}_linux_amd64.zip" cliproxyapi-credit-manager.so
mkdir -p "$CPA_DIR/plugins/linux/amd64"
cp cliproxyapi-credit-manager.so "$CPA_DIR/plugins/linux/amd64/"

# 3. 按 config.example.yaml 增加 plugins.configs 段，然后重启 CPA
```

> 归档里的 `LICENSE`、`README.md`、`metadata.json` 是发布记录，**不需要**复制到插件目录；
> 宿主只读取动态库本身。

### 数据格式

首次启动必须使用空 `data_dir`。插件在一个事务中创建完整当前结构，最后写入
`PRAGMA user_version=2`。同格式账本可正常重开；启动不会补列、修补结构或执行迁移。
其它格式会被拒绝且**不会被修改**，插件不会转换、静默清空或删除其中的数据；
**不提供自动迁移，也不建议执行清库或远程处理命令**。

当前格式与 v0.1.5 的 format 1 不兼容。需要升级或完全重新开始时，停止 CPA，
冷备整个旧 `data_dir` 作为独立档案并保留，再把配置指向新的空目录，重新创建客户端
Key、价格和调用方。不要直接清空或覆盖旧库。

### 卸载

删除库文件并移除 `plugins.configs` 中的配置块即可。**`data_dir` 不要随手删除**：里面
有 `pepper`，删掉之后所有客户端 Key 都无法再验证（见第 4 节）。

## 2. 配置项

配置写在 CPA 的 `config.yaml` 的 `plugins.configs.cliproxyapi-credit-manager` 下，
使用**严格解析**：出现未知键会直接报错并在日志中拒绝注册，所以拼写必须准确。

| 键 | 默认值 | 取值范围 | 说明 |
| --- | --- | --- | --- |
| `enabled` | 由宿主下发 | `true`/`false` | 宿主字段：只控制该实例开关，不影响全局 `plugins.enabled` |
| `data_dir` | `./data/cliproxyapi-credit-manager` | 非空 | 数据目录；相对路径按 CPA 工作目录解析为绝对路径；**运行期不可修改** |
| `history.retention_months` | `3` | 1..1200 | 历史保留月数（UTC 日历月） |
| `request_capture.enabled` | `false` | `true`/`false` | 是否启用请求快照 |
| `request_capture.retention` | `"24h"` | 正的 Go duration | 快照保留时长 |
| `request_capture.max_body_bytes` | `10485760` (10 MiB) | 1B..100MiB | 单个快照体积上限 |
| `request_capture.max_storage_bytes` | `1073741824` (1 GiB) | 1MiB..1TiB | 快照库物理上限（含 WAL） |

修改任何一项都需要宿主重新下发配置（重启 CPA，或通过宿主的管理接口触发热重载）。
`data_dir` 变更会被显式拒绝。

仅接受配置表中的插件字段，以及宿主注入的 `priority`、`store` 字段。
任何未知字段都会报配置错误并拒绝注册，不存在隐藏开关或旧配置转换。
CPA 的配置保存接口返回 200 只表示保存成功；宿主随后重新加载插件时仍会拒绝这些字段。
完整重载会卸载原插件，因此不得依赖原配置继续服务。

## 3. 数据目录与两个数据库

`data_dir` 下的文件：

```
data_dir/
├── credit.db         # 本地库（Key、价格、请求、用量、Token 计数）
├── credit.db-wal     # 同上，WAL
├── request-captures.db   # 请求快照库（可随时丢弃）
├── pepper            # 0600，客户端 Key 的 HMAC 密钥材料（首次启动生成）
└── lock              # 单实例目录锁
```

- **两个 SQLite 库相互独立**：`credit.db` 保存 Key、价格、用量日志与 Token 计数，
  不保存金额或价格快照；快照库只存诊断快照。快照库损坏或打不开时插件会降级为
  “快照关闭 + 健康告警”，**不影响**用量记录与推理。
- **单实例**：同一个 `data_dir` 同一时刻只允许一个进程打开（目录锁）。第二个进程会
  启动失败，这是有意设计——避免双重恢复或重复执行。
- `credit.db` 使用单连接、`synchronous=FULL`、`busy_timeout=5s`，提交即持久化。
  账本文件和 SQLite 辅助文件使用私有权限；已有账本丢失 `pepper` 时启动失败，
  不会生成新的密钥覆盖恢复线索，应还原成对备份。

## 4. 备份与恢复（务必遵守）

必须备份的内容是**整个 `data_dir`**（尤其 `pepper` 与 `credit.db`），并且：

1. **先停止 CPA，再备份**。运行中直接拷走在途状态可能不一致。
2. **`pepper` 必须与账本库成对保存**，不要分开、不要删除、不要重建。
   - 库中保存 HMAC 校验值及 AES-GCM 密文，只有同一 `pepper` 才能验证和解密客户端 Key；
   - 更换或丢失 `pepper` 会令所有客户端 Key 失效，也无法解密已封存的材料。
3. **只恢复当前格式的配套备份**：原样还原 `pepper` 与 `credit.db`（含 `-wal`），不要重新初始化。
4. 快照库 (`request-captures.db`) 可以不备份；它只是诊断数据。

建议做法：停机冷备整个目录并带上时间戳；把备份与 `pepper` 一起纳入受控密钥管理；
定期做一次“还原到空主机”的演练。

## 5. 保留与清理

- 历史默认保留 **3 个 UTC 日历月**（月末按日历钳位，例如 3 月 31 日往前一个月算到
  2 月 28/29 日）。
- 每次维护会删除**早于保留窗口且已关闭**的历史行（请求、用量），批量删除。
- **不删除**：未决（active/pending）请求、Key、价格配置、模型 Token 限额，以及
  **Token 耐久计数/重置基线**。金额不是耐久计数器：日志删除后，对应成本自然不再
  出现在报表中，也不存在“永久总支出”字段。
- 成本只反映仍在本地保留、且落在所选时间段的日志；保留窗口外的历史被删除后无法再查询
  或重算。
- 清理不会做整库 `VACUUM`，只做增量回收 + WAL 截断，且**每次回收有上限**，所以文件
  体积可能大于当前内容量。
- 如果 WAL 被占用导致检查点失败，健康状态会报告错误（不会假装成功）；下一次维护会
  再试。
- **历史幂等只在保留窗口内有效**：窗口外的旧请求行已被物理删除，迟到的用量事件无法
  “复活”这些请求；跨保留期的旧 `Admit` 也不再支持。

维护按固定节拍（约每分钟）自动执行，不需要人工干预。
这是删除过期历史并回收空间，不是压缩归档备份；需要长期审计时须自行受控备份。

## 6. 未决请求与成本显示

请求生命周期：`active`（在途，占用并发）→ 结束时进入 `pending`（用量待完整）或
`settled`（已完成）。状态只表示用量生命周期，不表示扣款/结算；**准入不预估、
不预留、不占用金额**。

出现下列情况时请求会**保持 pending**（在报表中可见），而不是被当成免费或已定价：

- 完全没有收到上游用量事件；
- 用量质量不可信（unknown）或不完整（partial）；
- 上游失败但无法证明用量为零。

pending **不冻结任何金额**，也**不会阻塞后续准入**：Token 配额按“实际已用”判断，
其他请求照常通过。**没有管理员金额裁决**：`/api/resolve` 已删除，
旧的人工 `release`/`charge` 调整不再存在。完整但未定价（缺价、金额溢出或
`per_image` 无真实出图数）的用量仍可正常 `settled`，只是 `cost_micro_usd: null`
并计入 `unpriced_executions`；显式全零价格才是已定价的免费 0。

`POST /api/reset-tokens` 只重置所选周期/Key 的 **Token 用量基线**，用于后续 Token
配额判断；它不修改日志、不改派生费用、不改美元预算，也不会清除未决请求。

> **崩溃语义**：上游用量事件经由宿主的内存队列送达插件，宿主队列不持久化。插件对
> 已提交的账本事务是持久化的（SQLite FULL 同步），但**不承诺崩溃安全的一次性记录**，
> 也不承诺任何丢失的事件一定会被补回。缺失用量的请求保持 pending，不会被伪造成免费。

## 7. 请求快照（默认关闭）

- 默认**关闭**。开启后抓取的是**执行入口的诊断快照**（请求 ID、入站请求头、入站请求
  体），**不是**最终发给上游的网络原始报文，也不是上游返回。
- 请求体在保留期间以 gzip 压缩保存；到期或超容量后删除，而非无限保留压缩档案。
- 管理员从使用统计请求详情查看；客户可用自己的插件 Key 在 `lookup.html` 查询，
  只返回该 Key 所属的请求。没有快照不代表没有用量记录。
- 单个快照体积上限、保留时长、物理上限见配置表；快照库的物理占用按**数据库文件 + WAL**
  统计，并预留一定余量，压力大时会**先淘汰最旧的快照**。
- 快照状态可能是：`disabled`（未开启）、`captured`、`oversize`（超限被跳过）、
  `dropped`（队列满等被丢弃）、`expired`（已过期）、`unavailable`（无证据可查）。
- 快照写入失败、超限或淘汰**永远不会**导致推理失败或成本展示变更。
- **脱敏有边界**：只对已知的敏感请求头与常见 JSON 敏感键替换为 `[redacted]`，不是
  匿名化承诺。非 JSON 请求体会原样保存；JSON 形态但解析失败、含重复键（包括转义后
  等价的键，例如 `"x"` 与 `"\u0078"`）、深度超过 256、节点数超过 100,000（键和值均计数）
  或含尾随内容的快照会丢弃，
  避免未经脱敏落盘。不要把快照当作合规 DLP 手段，
  也不要把它当作费用凭证（它可能已被淘汰或过期）。
- 快照的**请求 ID 上限为 128 UTF-8 字节**：超出上限的 ID 只计数为丢弃、既不进入内存状态环也不
  写入快照库，避免元数据无界增长。这是对宿主所提供 ID 的防御性上限，不是信任边界。
- 清理/回收依赖 SQLite 检查点；遇到 busy 时会报告错误并在下一次维护重试，**不保证
  立即完成**。

## 8. 插件职责边界

- 插件不发起后台模型请求，不调用宿主模型执行接口，也没有执行器、路由器或调度器。
- CPA 负责原生重试、失败切换、上游凭据选择和会话亲和。
- 未决用量可见，但不阻塞该 Key 或其它 Key 的后续准入。
- 准入只检查 Key 权限/过期、实际已用 Token 配额与显式并发限制，不读价格、不计算金额，
  也不预估、预留或占用；真实 Token 用量足额记录。

## 9. 故障与健康

`GET /api/health` 返回 `status`（`ok`/`degraded`）、`version`、`capture` 统计、
`retention_months`、`capture_enabled`、`last_error` 与当前配置。

- **维护/通知类错误按诊断上报**：维护失败与用量/完成通知错误会体现在健康信息与日志里，
  保留到成功重新配置或重启；成功维护不会自动清除告警，快照库还提供自身的错误统计。
- **准入按请求单独失败**：每次准入只因其自身的校验或存储错误失败（例如 Key 不允许该模型 → 403，
  实际已用 Token ≥ 配额 → 429）。价格缺失或价格规则禁用**不会**导致失败。
  **没有全局“永久熔断”标志**：一次瞬时错误或一个畸形/冲突事件
  不会永久阻断所有 Key 的后续请求。
- **维护类故障**（例如快照库异常）只影响健康状态与快照能力，不影响用量记录与推理。

常见问题：

| 现象 | 含义与处理 |
| --- | --- |
| 客户端 401 | 没有身份或身份未知：Key 未携带、拼写错误、被禁用或已过期 |
| 客户端 403 | Key 不允许该模型、已禁用或已过期；价格缺失不会导致 403 |
| 客户端 429 | Token 配额已用尽或 Key 并发触顶；这是软限制，实际已用 Token ≥ 配额后才拒绝下一次请求 |
| 客户端 5xx | 账本库不可用或该次准入出错：查看 `/api/health` 与 CPA 日志 |
| 管理 API 401 | 缺少/错误的 `Authorization: Bearer <管理密钥>` |
| 管理 API 415 | 非 GET 请求缺少 `Content-Type: application/json` |
| 配置被拒（启动/重载） | 对照配置表和 `config.example.yaml` 检查字段名与取值 |
| 管理 API 409 | 冲突：重复/相矛盾的请求 ID、重配置被拒（配置仍为旧值且仍生效） |
| 非当前账本格式 | 停止 CPA，保留旧 `data_dir` 冷备，配置新的空目录；不期待自动迁移，也不要直接清库 |
| 界面要求重新登录 | 正常行为：管理密钥只存在内存中 |

## 10. 上线前安全核对清单

- [ ] 已确认 **CPA 原生 `access.api-keys` 从未分发给调用方**（保持“未分发”状态）。
- [ ] 原生 Key 列表至少有一把高强度守卫 Key，且其中不包含插件客户 Key；原生列表为空
      不是安全部署，可能在插件缺失时放行匿名请求。
- [ ] `plugins.enabled: true`，库文件名与配置键均为发布时的 `cliproxyapi-credit-manager`。
- [ ] 首次运行使用空 `data_dir`；复用的数据仅来自当前格式。
- [ ] `data_dir` 位于受控存储，且已纳入包含 `pepper` 的整目录冷备。
- [ ] 配置仅含文档所列字段及宿主注入字段。
- [ ] 管理密钥为高强度口令，且只通过安全的带外渠道分发给管理员。
- [ ] 已实测误删/误停插件的后果：在上述守卫前提下，插件缺失时所有客户 Key 都被拒绝，
      上游调用为零；不把插件缺席时的安全错误归因于插件代码仍在执行。
- [ ] 快照若开启，已明确它不是 DLP、可能提前丢失，且不用于对账。
- [ ] 已确认本部署没有任何后台模型执行：插件不发起宿主执行回调，也不做定时探测。
